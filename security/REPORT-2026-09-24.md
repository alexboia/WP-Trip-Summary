## SEC-01 — Disclosure of track data from password-protected posts

### Finding and impact

`FrontendViewerPluginModule::addViewerToContent()` attaches the viewer without checking whether the post requires a password. Data may be added alongside the WordPress password form. Nonces for reading and downloading the track are generated in the same flow.

The AJAX read and download endpoints validate the nonce but do not recheck post visibility or password access. A previously available nonce must not replace current authorization, including after a change in post visibility. The additional REST field and JSON-LD output do not perform their own password checks.

A visitor may therefore obtain geographic information and details that the author expects the post password to protect. Downloading through the dedicated endpoint also depends on the download permission setting. Access to arbitrary private posts through ID enumeration alone was not demonstrated.

### Evidence

- [FrontendViewerPluginModule.php](../lib/pluginModules/FrontendViewerPluginModule.php), lines 176–205: attaching data and generating nonces.
- [GetTrackDataPluginModule.php](../lib/pluginModules/GetTrackDataPluginModule.php), lines 66–95: anonymous access with a nonce, without a visibility check.
- [DownloadTrackDataPluginModule.php](../lib/pluginModules/DownloadTrackDataPluginModule.php), lines 66–98: anonymous access with a nonce and a download setting check.
- [RestApiEnhancementsPluginModule.php](../lib/pluginModules/RestApiEnhancementsPluginModule.php), lines 94–115: supplying the additional field.
- [JsonLdFrontendDataPluginModule.php](../lib/pluginModules/JsonLdFrontendDataPluginModule.php), lines 70–95: emitting coordinates in the page.

The isolated probe invoked the actual content attachment flow using a password form and simulated services. Result: data and the nonce were attached, and the password check was never called.

### Solution outline

1. Introduce a shared access check for a post's trip summary: post existence, visibility to the current user, and satisfaction of password protection requirements.
2. Apply the check before rendering the viewer, generating nonces, emitting JSON-LD, supplying the REST field, and reading or downloading through AJAX.
3. Preserve legitimate editor and preview access through an explicit context that checks the appropriate post permissions.
4. For REST, respect WordPress's mechanism for passwords supplied in the request. On the frontend, use the WordPress password check; `current_user_can('read_post', $postId)` alone does not cover all conditions.
5. Recheck access on every request, including when data is already cached.

**Verification after remediation:** a matrix covering anonymous visitors, users without access, and authorized authors/editors, for public, password-protected, private, and draft posts; test correct and incorrect passwords, and a nonce obtained before access to the post was restricted.

## SEC-02 — Incomplete protection for stored files

### Finding and impact

Uploads are assembled into predictable files named `track-ID.dat`, in the tracks directory, which is located under uploads by default. Generated rules block the `cache`, `gpx`, `geojson`, and `kml` extensions but omit `dat`. A temporary file may be directly accessible during an upload or after an abandoned upload if no other server rules protect it.

Protection for tracks, cache files, and logs relies on `.htaccess`. Servers that do not apply these rules require equivalent restrictions. An `index.php` file does not prevent direct access to a file with a known name.

### Evidence

- [Default.php](../lib/route/track/processor/Default.php), lines 45, 294–302, and 379–388: temporary extension and file names.
- [CreateTracksStorageDirSecurityAssets.php](../lib/installer/service/CreateTracksStorageDirSecurityAssets.php), lines 73–79: protected extensions.
- [CreateLogStorageDirSecurityAssets.php](../lib/installer/service/CreateLogStorageDirSecurityAssets.php), lines 66–69: log protection.
- [Env.php](../lib/Env.php), lines 269–277: default location under uploads.

The existing local rules for the tracks directory have the same omission of the `.dat` extension.

### Solution outline

1. Block HTTP access to the plugin's entire data directory instead of relying on a list of extensions. Legitimate downloads should be served through authorized endpoints.
2. As an immediate measure, include the `.dat` extension and update the rules on existing installations.
3. Prefer storage outside the public document root where the infrastructure allows it; otherwise, document the rules for each supported server.
4. Use separate temporary files for each upload session and remove abandoned files after a defined interval. Hard-to-guess names provide only additional protection.

**Verification after remediation:** direct HTTP requests to synthetic `.dat`, `.gpx`, `.cache`, and `.log` files, including during an unfinished upload; expected response: 403/404. Separately verify authorized downloads through the application.

## SEC-03 — Stored XSS through map attribution

### Original finding and impact (2026-09-24)

`getTileLayerAttribution()` originally concatenated the configured URL directly into the `href` attribute. Text filtering and URL validation accepted certain values containing quotation marks that allowed an HTML event attribute to be injected. The data reached the Leaflet control, which inserted it through `innerHTML`.

Exploitation requires permission to manage plugin settings, available to administrators by default. This is not an attack path for anonymous visitors or authors with default permissions. The trust boundary is particularly relevant in multisite installations and for delegated roles without permission to publish arbitrary JavaScript.

### Original evidence

- [abp01-map.js](../media/js/abp01-map.js), lines 330–345: HTML construction.
- [Url.php](../lib/validate/Url.php), lines 86–96: URL validation.
- [abp01-plugin-functions.php](../abp01-plugin-functions.php), lines 436–459: the `ARRAY_A` branch of `abp01_esc_js_object()` preserves values unchanged.
- [leaflet-src.js](../media/js/3rdParty/leaflet/leaflet-src.js), line 5701: inserting attribution through `innerHTML`.

The local probe passed a synthetic value through filtering, validation, and the conversion used for settings. Parsing the resulting HTML confirmed the attribute `onmouseover="window.auditMarker=1"`. No attack was executed in a browser, and no settings were saved to the database.

The complete attribution URL used in the follow-up reproduction was `https://example.com/"onmouseover="window.auditMarker=1`, without a space before `onmouseover`. The event attribute shown above was the parsed output, not a standalone URL to enter in the settings form.

### Reevaluation — 2026-10-07

**Conclusion: the original attribute/text injection is remediated in the reviewed code.**

- [abp01-map.js](../media/js/abp01-map.js), `getTileLayerAttribution()`: creates an `a` or `span`, assigns the label through `textContent`, and returns `outerHTML`. The URL is assigned through `href`; it is no longer concatenated into HTML. The link also uses `rel="noopener noreferrer"`.
- [SettingsPluginModule.php](../lib/pluginModules/SettingsPluginModule.php), `_createTileLayerValidationRule()`: explicitly restricts attribution URLs to `http://` and `https://`. This is the current settings rule, even though the generic `Abp01_Validate_Url` class has a broader default protocol list.
- The original quote-containing URL still passes validation, but the actual renderer serializes it as an attribute value and, when used as the fallback label, as plain text. No event attribute or extra element was produced by the DOM probes.

**Verification performed:**

1. Executed the actual `getTileLayerAttribution()` function extracted from the current JavaScript file using jsdom 26.1.0, then reparsed its returned HTML: **16 cases passed**. Cases covered the original URL payload, URL-as-label fallback, apostrophes, HTML entities, HTML/script labels in both branches, Unicode, an already encoded URL, and empty/null/undefined values. Assertions checked element count, absence of child elements and event attributes, exact label text, and preservation of the URL attribute. Script execution was disabled.
2. Invoked the actual controller's POST reader and tile-layer validation rule with WordPress text sanitization, simulated request slashing, and isolated translation/filter services: **18 cases passed** on PHP 8.4.0. HTTP/HTTPS and the harmlessly rendered quote payload were accepted; JavaScript variants, data, VBScript, file, FTP/FTPS, mailto, and relative URLs were rejected. These probes did not invoke the authenticated AJAX dispatcher or save settings.
3. JavaScript syntax validation passed.

**Remaining boundary:** the renderer itself does not reject an unsafe protocol supplied directly in its options. A separate probe confirmed that bypassing the settings validator can leave a `javascript:` value in `href`. No path through the current settings workflow that bypasses its protocol restriction was established. Imports, migrations, or other future settings writers must enforce equivalent validation; validating again when rendering would provide additional protection for pre-existing or externally modified settings.

No full settings-page save-and-view workflow or browser event execution was performed. The conclusion concerns the demonstrated injection and the current settings validation path.

### Remediation approach

1. Build the link with `document.createElement('a')`, assign the URL through the appropriate DOM property or API, and assign the text through `textContent`. When no URL is configured, use a `span` with `textContent` so that attribution text remains protected in both branches.
2. If the Leaflet API requires an HTML string, serialize the element constructed this way instead of concatenating values.
3. Restrict URL schemes to those required by the feature, usually HTTP and HTTPS.
4. Treat attribution text as plain text. Validation when saving complements, but does not replace, protection when rendering.

**Verification after remediation:** values containing quotation marks, apostrophes, HTML entities, and disallowed schemes; the resulting DOM must not contain event attributes or additional elements. Verify legitimate attribution values and Unicode characters.

### Remediation rationale — DOM construction instead of `encodeURI()`

The implementation reviewed on 2026-09-26 creates an `a` element when an attribution URL is present and a `span` otherwise. Both branches assign the label through `textContent` and return `outerHTML` for Leaflet. This keeps the label as text and lets DOM serialization escape attribute values and text for HTML output.

Applying `encodeURI()` to the URL would encode the double quotes in the demonstrated payload, preventing that particular escape from the double-quoted `href` attribute. It is unsuitable as the general rendering protection for the following reasons:

- **Double encoding:** an existing escape such as `%20` becomes `%2520`. Applying it to an already encoded URL can change the requested resource, query values, or URL signatures.
- **Different encoding context:** it preserves apostrophes and ampersands, so it does not provide HTML attribute escaping. Protection must account for the HTML context, including its attribute delimiters.
- **No protocol validation:** a value such as `javascript:window.auditMarker=1` remains unchanged. Allowed URL schemes must be checked separately; assigning a value through the DOM `href` property does not perform this security check either.
- **No protection for separately concatenated text:** encoding the URL does not protect the attribution label. Using `textContent` for both `a` and `span` covers the label, including when the URL is used as its fallback.
- **An additional error case:** an unpaired UTF-16 surrogate causes `URIError`, which would need handling if this function were added to the rendering path.

The encoding behavior and exception are defined by the [ECMAScript `encodeURI` and `Encode` algorithms](https://tc39.es/ecma262/multipage/global-object.html#sec-encodeuri-uri). This rationale records the implementation choice; the scope and results of subsequent verification are stated in the dated reevaluation above.

## SEC-04 — Directory traversal in the Leaflet wrapper

### Original finding and impact (2026-09-24)

The public script that wraps Leaflet extensions accepts the `load` parameter. The original filtering permitted `../` sequences, and the regular expression checked the shape of the path without validating its canonical location. The path was concatenated with `ABSPATH` and read by PHP.

The local probe confirmed that a script outside the permitted Leaflet extensions directory could be read. Impact depends on the presence of nonpublic JavaScript files accessible to the PHP process. Reading remains limited to `.js` files; reading PHP files, executing code, or modifying files was not demonstrated.

### Original evidence

- [abp01-plugin-leaflet-plugins-wrapper.php](../abp01-plugin-leaflet-plugins-wrapper.php), lines 98–117, 139–150, and 164–167.
- The local input `media/js/3rdParty/leaflet-plugins/../../abp01-map.js` caused the wrapper to return the `abp01-map.js` script.

### Reevaluation — 2026-10-07

**Initial reevaluation result:** ordinary traversal was remediated, but a conditional Windows junction-chain bypass remained. The subsequent dynamic-resolution fix and its verification are recorded below.

Before the follow-up fix, [abp01-plugin-leaflet-plugins-wrapper.php](../abp01-plugin-leaflet-plugins-wrapper.php) resolved the requested path through one `realpath()` call and checked it against the canonical `media/js/3rdParty/leaflet-plugins` directory. The allowed prefix included a trailing directory separator, preventing a sibling directory with a similar name from satisfying the prefix check. The resolved target also had to have a `.js` extension. This blocked the original `../` payload, but the containment check depended on the returned path having no unresolved links. On Windows, PHP documents that directory junctions and symbolic links are expanded by only one level. [PHP `realpath()` documentation](https://www.php.net/manual/en/function.realpath.php).

**Verification performed:**

1. Ran [bin/tools/test-leaflet-wrapper.php](../bin/tools/test-leaflet-wrapper.php) against the local Apache host `http://alexboia.net.local:8080` with `--mode=all`, covering both `load` and rewrite entry points. The unchanged runner reported **39 passed, 23 failed**. All failures were script-content comparisons caused by its Windows newline handling: actual output was normalized to LF, while expected output still inserted `PHP_EOL` (CRLF) around the wrapper.
2. Reran a temporary copy of that runner with both expected and actual output normalized to LF: **62 passed, 0 failed**. No production code or repository test was changed. This covered the three legitimate scripts, headers/cache behavior, missing and non-JavaScript files, traversal within/outside the plugin, encoded/backslash variants, array/null-byte inputs, and precedence between `load` and the rewritten request path.
3. Additional HTTP probes returned **404 with no fixture content** for the original report payload, an existing sibling directory named with the allowed directory's prefix, and a single Windows directory junction inside the allowed tree pointing to that sibling.
4. An additional probe with **two chained junctions** returned **HTTP 200 containing the outside file's marker**. This was reproduced twice with different temporary fixtures. The CLI probe showed `realpath(audit-a/marker.js)` returning a path through `audit-b` that still matched the allowed prefix; reading that returned path followed the remaining junction to the outside file. Synthetic files and junctions were removed afterward. Linux symbolic links were not tested.
5. PHP syntax validation passed.

**Confirmed residual bypass:**

```text
media/js/3rdParty/leaflet-plugins/audit-a -> audit-b (inside the allowed directory)
media/js/3rdParty/leaflet-plugins/audit-b -> ../leaflet-plugins-audit (outside it)
media/js/3rdParty/leaflet-plugins-audit/marker.js contains a synthetic marker

load=media/js/3rdParty/leaflet-plugins/audit-a/marker.js
Result: HTTP 200, wrapped contents of the outside marker.js
```

The request alone cannot create these junctions. Exploitation requires a suitable existing chain or permission to create links inside the allowed tree, and a readable `.js` target. No such pre-existing chain was identified during this review. The probe establishes a conditional read outside the intended boundary, not unauthenticated filesystem modification or PHP execution.

**Selected follow-up:** retain dynamic serving and fully resolve directory-link chains before checking containment. The existing 62 HTTP cases did not cover the junction-chain bypass, so a separate regression suite was added with the fix below.

**Follow-up issues, separate from the original traversal:**

- **Test portability — corrected:** normalize the complete expected wrapper output in `wpts_leaflet_test_script_content()` before comparing it with normalized actual output. The repository HTTP suite now passes on this Windows CLI without a temporary runner patch.
- **Current-working-directory dependency — corrected:** the resolver now anchors the candidate to `__DIR__`. Previously, an isolated probe accepted a legitimate script with the plugin directory as CWD and rejected it with the WordPress root as CWD. A regression test now serves a dynamic fixture successfully with the system temporary directory as CWD.
- **Conditional byte-length defect:** `wpts_wrapper_serve_script()` uses `mb_strlen()` when available for `Content-Length`. With a UTF-8 internal encoding this counts characters, whereas the header needs bytes; use `strlen($content)`. An isolated UTF-8 example measured 8 characters versus 10 bytes. A synthetic Unicode script was served intact by the current local HTTP configuration, so truncation was not reproduced there. See the [PHP length semantics](https://www.php.net/manual/en/function.mb-strlen.php) and [HTTP Content-Length definition](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6).

Concurrent filesystem replacement by a party with write access was not tested; the confirmed junction-chain bypass did not require a race.

### Implemented dynamic-resolution fix — 2026-10-07

The production change is confined to `wpts_wrapper_expand_to_disk_path()`. It anchors paths to `__DIR__`, rejects null bytes, clears the relevant realpath cache entry, and repeatedly resolves each returned path until it is unchanged. Failed resolution, a repeated non-stable path, or failure to converge within 32 calls returns `null`. A resolved directory retains the trailing separator required by the existing function contract. The existing containment and `.js` checks therefore receive the final path instead of an intermediate junction path. No fixed list of script names was introduced.

**Post-fix verification:**

- [tests/test-LeafletWrapper.php](../tests/test-LeafletWrapper.php): **11 tests / 11 assertions passed**, exercising the actual wrapper in isolated PHP processes. Cases include dynamic and root-relative paths, a different CWD, internal/external junction chains, one external junction, sibling-prefix collision, the original traversal, directories, missing/non-JavaScript files, and a Windows chain exceeding the resolution bound. Junctions and fixtures are created and removed by the suite.
- [bin/tools/test-leaflet-wrapper.php](../bin/tools/test-leaflet-wrapper.php): **62 passed, 0 failed** against the local Apache host, with the newline comparison corrected in the repository runner.
- Additional Apache probes for both `load` and rewrite routes: the two-junction external chain returns **404 without marker content**; the two-junction internal chain returns **200 with the expected fixture script**.
- Isolated checks confirmed the directory trailing-separator contract and null-byte rejection. PHP syntax checks passed.

Run the regression suite without WordPress or a database:

```text
php vendor/bin/phpunit --no-configuration --bootstrap tests/bootstrap-unit.php --do-not-cache-result --test-suffix test-LeafletWrapper.php tests
```

**Scope:** the demonstrated static-chain bypass is closed in the tested Windows setup. Concurrent filesystem replacement remains outside this guarantee; the enclosing wrapper still resolves input separately when validating and locating the file. The `mb_strlen()`/`Content-Length` follow-up remains unchanged. Linux symlink behavior has not been executed locally; the new suite uses symlinks on non-Windows systems and junctions on Windows.

### Original solution outline

1. Replace arbitrary paths with an explicit mapping between identifiers and the few supported Leaflet scripts.
2. Canonicalize paths through `realpath()` and verify that they remain within the permitted directory, including after resolving symbolic links.
3. Reject unknown inputs before reading the file. Retain extension checks as an additional measure.

**Verification after remediation:** legitimate scripts continue to work; traversal inputs, paths to other plugins, and symbolic links pointing outside the permitted directory do not return content.

## SEC-05 — Resource exhaustion through track geometry

### Finding and impact

Track simplification uses a recursive Douglas–Peucker implementation that traverses and copies lists. An upload file size limit exists, but there is no explicit limit on point count or processing cost. Public reads may trigger simplification when the cache is missing.

An account with permission to upload tracks can supply expensive geometry. Processing such tracks, particularly concurrently and without a cache, may occupy PHP workers or consume available memory. This consequence is an estimated risk; server unavailability was not induced.

### Evidence

- [Line.php](../lib/route/track/Line.php), lines 139–165: recursive algorithm.
- [Default.php](../lib/route/track/processor/Default.php), lines 213–233: on-demand simplification.
- [GetTrackDataPluginModule.php](../lib/pluginModules/GetTrackDataPluginModule.php), lines 93–95: invocation during track reads.

Local measurements on synthetic zigzag geometry, using the actual distance calculation:

| Point count | Distance calculations | Approximate time |
| --- | --- | --- |
| 250 | 8,524 | 0.015 s |
| 500 | 35,771 | 0.070 s |
| 1,000 | 185,873 | 0.294 s |

These values illustrate cost growth, not production server capacity.

### Solution outline

1. Set explicit limits on accepted point counts, segment counts, and nesting depth.
2. Precompute the simplified representation during import, in a process with controlled time and memory budgets.
3. Avoid expensive processing in public requests; use the precomputed result and return a controlled response when it is unavailable.
4. Introduce a mechanism to prevent simultaneous recalculation of the same track and define safe behavior when limits are exceeded.

**Verification after remediation:** ordinary tracks, small pathological geometries, and inputs at the accepted limit; concurrent requests with a missing cache in an isolated environment. Verify limits and recovery after processing is interrupted.

## SEC-06 — JavaScript libraries missing security fixes

### Finding and impact

The copies bundled with the plugin include:

- **Chart.js 2.9.3**, predating the prototype pollution fix associated with CVE-2020-7746; the fix was included in 2.9.4.
- **URI.js 1.19.2**, predating several security fixes concerning URL interpretation.

The presence of these versions is confirmed. It was not demonstrated that an attacker can control the parameters required for exploitation through the plugin's existing flows. The severity of a library vulnerability does not automatically apply to the entire plugin.

### Evidence and references

- [Chart.js](../media/js/3rdParty/chartjs/Chart.js), line 2.
- [URI.js](../media/js/3rdParty/uri/URI.js), line 4.
- [Chart.js fix in the official project](https://github.com/chartjs/Chart.js/pull/7920).
- [CVE-2020-7746 advisory](https://github.com/advisories/GHSA-h68q-55jf-x68w).
- [Official URI.js changelog](https://github.com/medialize/URI.js/blob/gh-pages/CHANGELOG.md).

### Solution outline

1. Inventory the libraries actually shipped in `media/js/3rdParty`, including bundle and minified files; the current npm manifests do not automatically cover them.
2. Update the copies to compatible versions containing the required fixes. For Chart.js, 2.9.4 is the threshold for the cited fix, not a general recommendation for the current version to use.
3. Update the variants used in production and the asset cache identifiers.
4. Introduce a reproducible record of versions and periodic advisory checks.

**Verification after remediation:** map and altitude profile loading, AJAX URL construction, administrative forms, and confirmation of the versions of files actually served.

## SEC-07 — Unsafe cache deserialization

### Finding and impact

Reading documents and altitude profiles from the cache uses `unserialize()` without restricting classes. A local probe confirmed execution of a synthetic class's `__wakeup()` method.

Exploitation requires an attacker to be able to modify cache files or the serialized source through another vulnerability. No such path was identified. The risk of code execution also depends on the available classes and their behavior; this is not a demonstration of RCE through the plugin's endpoints.

### Evidence

- [Document.php](../lib/route/track/Document.php), lines 76–80.
- [AltitudeProfile.php](../lib/route/track/AltitudeProfile.php), lines 55–59.
- [Default.php](../lib/route/track/processor/Default.php), lines 108–112 and 240–254: reading cache files.

### Solution outline

1. Prefer a data format without automatic class instantiation, such as JSON, with explicit reconstruction of objects after validation.
2. As an interim measure, use a restrictive `allowed_classes` list and validate the resulting type and internal structure. Classes of nested objects must be explicitly inventoried.
3. Treat invalid cache data as a cache miss without using it partially. Invalidate the old format during migration.
4. Maintain restrictive storage permissions. Blocking HTTP reads does not replace protection against unauthorized writes.

**Verification after remediation:** an object of a disallowed class does not execute its deserialization methods; corrupted files or files in the old format are rejected in a controlled manner; legitimate tracks are reconstructed correctly.

## Proposed remediation order

1. **SEC-01 and SEC-02:** close data disclosure paths and protect storage.
2. **SEC-04 and SEC-03:** restrict the files served by the wrapper and eliminate unsafe HTML concatenation.
3. **SEC-05 and SEC-06:** introduce processing limits and concurrency control, and update bundled libraries.
4. **SEC-07:** migrate the cache format or restrict deserialization, invalidating existing caches.

## Verification limitations

- The original audit did not perform live site testing. The 2026-10-07 SEC-04 reevaluation added HTTP tests against the local development host only. No database changes or server load tests were performed.
- The SEC-03 reevaluation used an HTML DOM implementation with script execution disabled and isolated controller validation; it did not exercise the complete authenticated settings UI or execute events in a browser.
- The isolated probes confirm the described behaviors but do not replace complete verification in a WordPress staging environment.
- `composer audit --locked --no-dev --format=json` could not contact Packagist from the available environment. The automated PHP dependency audit remained incomplete.
- No XXE vulnerability was confirmed in the GPX probe on PHP 8.4.0 / libxml 2.11.9: the external entity loader was not called, and the test entity was not expanded. Using SimpleXML alone is not evidence of XXE; see also the [PHP documentation](https://www.php.net/manual/en/function.libxml-disable-entity-loader.php).
- This report applies to the local copy reviewed on the stated date, not to all published versions or unverified server configurations.
